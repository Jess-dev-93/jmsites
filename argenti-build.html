One system, built to keep evolving

As the website expanded, one-off classes, repeated overrides and page-specific decisions became harder to trace. The answer was not another quick fix. It was clearer ownership across the whole build.

Spacing made this especially obvious. A section could look finished in one view, then behave differently when it was published or tested at another breakpoint. I stopped treating every spacing issue as a separate problem and started tracing which shared system actually owned the layout.

Typography, wrappers, grids, buttons, colour treatments and common components were brought into a reusable foundation. Existing page systems were consolidated where it helped-without rebuilding working sections purely for the sake of making every class name match.

Where Webflow stopped being simple

CMS relationships, custom code, responsive behaviour and third-party scripts can all affect the same visible result. This was the part of the build where careful debugging mattered more than adding another workaround.

Custom CSS JavaScript Finsweet HubSpot DevTools GTM GA4 Consent Mode

The Case Study filters

The filter interface looked simple, but its behaviour depended on CMS categories, capability and industry values, Finsweet attributes, template output and colour logic all working together.

Instead of continuing to change what was visible, I inspected the live published state in DevTools and traced the issue back through the systems that actually controlled it.

  1. See the symptom
  2. Inspect the live state
  3. Find the system that owns it
  4. Fix the source
  5. Verify the result

The visible problem is not always where the problem lives. Once I stopped asking “what can I add to fix this?” and started asking “which system owns this behaviour?”, the debugging became much clearer.

I am strongest where Webflow stops being simple.
